> **Summary**: 매일 크롤링된 `TechNews`를 분석해 "오늘의 개발 트렌드"를 별도 콘텐츠로 홈 화면에 노출하고, 그 분석 결과를 근거로 `DailyKnowledge`(일일 학습 게시물) 생성 프롬프트를 채운다
>
> **Project**: dailyDevInsight

## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | 현재 `TechNews`(뉴스 크롤링)와 `DailyKnowledge`(AI 일일 학습 지식 생성)가 완전히 분리된 파이프라인이다. `DailyKnowledgeGenerationService.renderPrompt()`는 `${date}/${category}/${tone}/${difficulty}`만 치환할 뿐 크롤링된 뉴스를 전혀 참조하지 않아, 학습 게시물이 "요즘 실제로 무슨 뉴스가 있었는지"와 무관하게 생성된다 |
| **Solution** | 매일 수집된 `TechNews`를 LLM으로 분석해 "오늘의 개발 트렌드"(신규 콘텐츠)를 생성·저장하고, 홈 화면에 별도 카드로 노출한다. 이어서 그 트렌드 분석 결과를 `DailyKnowledge` 생성 프롬프트에 참조시켜, 오늘 배우는 지식이 실제 뉴스 흐름에 근거하도록 연결한다 |
| **Function/UX Effect** | 사용자는 홈 화면에서 "오늘의 개발 트렌드" → "오늘의 개발 지식" 순서로, 왜 오늘 이 주제를 배우는지 흐름을 눈으로 확인할 수 있다 |
| **Core Value** | "급속도로 변하는 개발 시장에 맞춰 최신 정보를 획득·학습한다"는 서비스 본래 취지를, 크롤링 → 트렌드 분석 → 학습 콘텐츠 생성으로 이어지는 파이프라인으로 실제 구현해 포트폴리오상 AI 활용 스토리를 명확히 한다 |

## Context Anchor

| **WHY** | 2026-08-13 PM 세션에서 사용자가 프로젝트 제작 동기("급속도로 변하는 개발 시장에 맞는 최신 정보 학습")를 재확인하면서, 당초 "뉴스 크롤링"과 "AI 일일 지식 생성"을 별개로 만들려던 계획을 "뉴스 기반 트렌드 분석 → 그 분석으로 학습 게시물 생성" 구조로 전환하기로 결정. 이는 `weekly-ai-insight-hashtag.md` Plan §1.2에서 "별도 설계 필요"로 범위 밖 처리했던 항목("해시태그/요약 결과를 일일 지식 생성 프롬프트에 참조")을 정식 착수하는 것 |
| **WHO** | 인증 여부 무관 홈 화면 방문자(트렌드·학습 게시물 열람), 관리자(생성 트리거) |
| **RISK** | (1) LLM 응답 스키마가 신규 추가되므로 `LlmGenerationClient` 계열(`OpenAiLlmGenerationClient`, `MockLlmGenerationClient`) 동시 갱신 필요. (2) `DailyKnowledge` 생성이 트렌드 분석 결과에 의존하게 되면, 트렌드 생성이 실패하거나 그날 크롤링된 뉴스가 없을 때 학습 게시물 생성 전체가 막히지 않도록 폴백 전략이 필요 → **가용성 우선으로 확정(§6)**. | **SUCCESS** | (조건부 정의, Codex 2차 검증 반영) 기준일 트렌드 생성이 **성공한 경우**: 트렌드가 홈에 노출되고 같은 날 `DailyKnowledge`가 그 트렌드를 반영한 프롬프트로 만들어진다. 트렌드 생성이 **실패/부재인 경우**: `DailyKnowledge`는 트렌드 없이 기존 방식으로 정상 생성되고 "트렌드 미반영" 상태가 이력에 기록된다 — 두 경로 모두 "정상 동작"이며, 트렌드 생성 자체의 일일 성공률은 별도 운영 지표로 관리한다(무조건 매일 반영을 성공 기준으로 삼지 않는다) |
| **SCOPE** | 일간 트렌드 "생성 + 저장 + 카드 노출 + DailyKnowledge 프롬프트 참조"까지만 포함. 기존 `WeeklyAiInsight`(주간)는 이번 기능에서 수정하지 않는다 — 별개로 유지(사용자 확정, 2026-08-13) |

## 1. Overview

### 1.1 Purpose

매일 크롤링된 `TechNews`를 분석해 "오늘의 개발 트렌드"를 신규 콘텐츠로 생성하고, 이를 `DailyKnowledge`(일일 학습 게시물) 생성의 입력 근거로 연결하여, 크롤링 → 트렌드 분석 → 학습 콘텐츠 생성이 하나의 흐름으로 이어지도록 한다.

### 1.2 Background

- 최초 구상: "AI가 일일 지식을 생성하는 기능"과 "뉴스만 크롤링하는 기능"을 각각 독립적으로 제공
- 실제 코드 확인 결과, 두 기능은 지금도 완전히 분리되어 있음(`DailyKnowledgeGenerationService.renderPrompt()`가 `TechNews`를 참조하지 않음)
- 2026-08-13 PM 세션에서 사용자가 "수집한 뉴스 기반으로 개발 트렌드를 분석하고, 해당 정보로 일일 학습 게시물을 만드는 방향"으로 전환을 요청
- 노출 방식 논의: (A) 트렌드 분석을 비노출 내부 입력으로만 사용 vs (B) 트렌드 분석 자체를 별도 콘텐츠로 노출 후 학습 게시물과 연결 — 사용자가 **B안**을 선택(트렌드 → 학습 게시물로 이어지는 과정 자체를 사용자에게 보여주는 것이 포트폴리오 스토리상 더 가치 있다고 판단)
- 기존 `WeeklyAiInsight`(주간 트렌드 분석)와의 관계 논의: 합치지 않고 **별개 유지**로 결정(성격이 다름 — 주간은 종합 서술형 3문단, 일간은 가벼운 트렌드 요약. 기존 안정적인 파이프라인에 손대는 회귀 위험도 회피)

### 1.3 Related Documents

- `docs/01-plan/features/weekly-ai-insight.md`, `docs/02-design/features/weekly-ai-insight.md` — 참고할 기존 뉴스 기반 LLM 분석 파이프라인(구조는 유사하되 본 기능과는 독립적으로 유지)
- `docs/01-plan/features/weekly-ai-insight-hashtag.md` §1.2 — 본 기능의 시작점이 된 "프롬프트 참조 연동" 후속 과제 언급
- `docs/01-plan/features/service-quality-roadmap.md` — 로드맵과의 중복 여부 확인 필요(후속 검토)

## 2. Scope

### 2.1 In Scope

- [ ] 매일 수집된 `TechNews`를 분석해 "오늘의 개발 트렌드"(신규 콘텐츠)를 생성하는 LLM 연동 추가
- [ ] 신규 엔티티(가칭 `DailyTrendInsight`) + Repository + 저장/조회 Service
- [ ] 홈 화면에 "오늘의 개발 트렌드" 카드 신설 — 기존 `weekly-ai-insight-section`과 `dailyKnowledgeChunks` 슬라이더 사이에 배치
- [ ] `admin/crawling.html`에 `[오늘의 개발 트렌드]` 탭 신설(§6 확정) — 기존 `weeklyInsight` 탭과 동일 패턴으로 생성/재생성 트리거, 미리보기 카드, `visible` 토글 제공. 신규 관리자 페이지는 만들지 않음
- [ ] 트렌드 컨텍스트를 **사용자 프롬프트 템플릿 내용과 무관하게 서버가 항상 강제로 덧붙이는 방식**으로 구현(§6 Key Decisions) — 템플릿에 `${dailyTrend}` 변수가 없어도, 또는 관리자가 수동 편집 화면에서 프롬프트 본문을 지워도 실제 LLM 호출에는 트렌드 컨텍스트가 별도 구역으로 항상 포함됨. `${dailyTrend}` 변수는 관리자가 트렌드 삽입 "위치"를 커스터마이징하고 싶을 때 쓰는 선택적 수단으로만 제공(변수가 없으면 프롬프트 말미에 자동 추가)
- [ ] 위 강제 추가 로직은 예약 생성(`renderPrompt` 경로)과 수동 생성 **두 곳 모두**에 적용 — 특히 수동 생성은 `buildRenderedPromptForManual`이 화면을 처음 열 때만 프롬프트를 렌더링하고, 이후 관리자가 textarea에서 자유롭게 편집한 텍스트를 `previewManualGeneration`이 그대로 LLM에 전달하는 구조이므로, "템플릿 렌더링 시점에 변수를 치환"하는 방식만으로는 이 경로를 보장할 수 없음 — LLM 호출 직전 단계에서 트렌드 컨텍스트를 별도로 덧붙이는 공통 로직 필요
- [ ] LLM이 반환한 트렌드 응답에 대한 형식 검증(확정, Codex 2차 검증 반영 — `weekly-ai-insight-hashtag.md` §3.2와 동일 원칙): 공백 키워드 제외 및 중복 제거 후 개수를 센다. 3개 미만이면 생성 실패로 처리, 5개 초과면 실패시키지 않고 **앞 5개만 사용**. 요약이 비어 있으면 실패로 처리
- [ ] 관리자 수동 생성 확인 화면(`generation.html`/`generation-compose.html`)에 해당 프롬프트에 반영된 트렌드 내용을 **읽기 전용 구역**으로 표시 — 관리자가 결과물 검수 시 근거를 확인할 수 있어야 하며, 편집 가능한 프롬프트 textarea와는 분리되어야 함(위 강제 추가 방식과 일관)
- [ ] `DailyKnowledge`(또는 `GenerationHistory`)에 생성 시점에 사용된 트렌드 스냅샷/식별자를 저장 — 관리자가 이후 트렌드를 재생성해도 "이 지식이 어떤 트렌드를 근거로 만들어졌는지" 추적 가능해야 함(§6 재생성 정책과 연결). **수동 생성 경로에서는 "저장 시점의 최신 트렌드"가 아니라 "미리보기 LLM 호출에 실제 사용된 트렌드"를 저장**해야 함 — `previewManualGeneration()`이 호출 시점의 트렌드 스냅샷을 `GenerationPreviewResponse`에 함께 담아 반환하고, `saveManualGenerationFromPreview()`가 (제목/요약/본문을 그대로 저장하는 기존 방식과 동일하게) 그 스냅샷을 그대로 저장한다 — 저장 시점에 트렌드가 이미 재생성되어 있어도 미리보기 당시 값을 사용(Codex 2차 검증 반영: 미리보기↔저장 사이 트렌드 재생성 시나리오)
- [ ] `ScheduledGenerationExecutor` 내에서 트렌드 생성 → (성공 여부 무관, 예외 격리) → 학습 게시물 생성 순으로 순차 호출. 트렌드 생성 단계는 자체 예외를 잡아 로그로만 남기고 학습 게시물 생성 단계로 전파하지 않음
- [ ] 그날 크롤링된 뉴스가 없거나 트렌드 생성이 실패한 경우의 폴백 정책 적용(§6: 가용성 우선 — 트렌드 없이도 기존 방식대로 학습 게시물 생성 진행, 해당 상태는 이력에 기록)
- [ ] 트렌드 분석용 뉴스 입력 상한/비용 정책 정의 — 기존 `WeeklyAiInsightService`가 최대 40건·뉴스당 요약 350자로 제한하는 것과 동일한 수준의 상한을 3일 폴백 윈도우에도 적용(크롤링이 실행당 최대 100건까지 쌓일 수 있어 무제한 입력 방지 필요)

> **변경 불필요**: `GenerationSchedule`의 필드(예약 시각, 카테고리/톤/난이도 프리셋, 중복 허용 여부)는 구조 변경 없이 그대로 유지. 단, 해당 스케줄의 실행 트리거가 이제 트렌드 생성 시점도 함께 결정하게 되는 "동작 의미"의 확장은 있음(필드/구조 변경 아님)

### 2.2 Out of Scope

- 기존 `WeeklyAiInsight`(주간 트렌드 분석) 파이프라인 수정 — 이번 기능과 완전히 별개로 유지
- 일간 트렌드를 모아 주간 트렌드를 만드는 집계 연동(향후 자연스러운 확장 후보이나 이번 범위 아님)
- 트렌드 카드 클릭 시 관련 뉴스/게시물로 딥링크되는 인터랙션
- 관리자의 트렌드 수동 편집(텍스트/키워드 직접 수정) UI — 범위 밖. `visible` 단순 토글(노출/비노출)은 홈 노출 기준(§6: 최신 공개 트렌드 1건)을 지원하기 위해 In Scope로 확정(`WeeklyAiInsight`와 동일 수준)
- 과거(기능 도입 이전) 날짜에 대한 소급 트렌드 생성

## 3. Requirements

### 3.1 Functional Requirements

| ID | Requirement | Priority | Status |
|----|-------------|----------|--------|
| FR-01 | 관리자가 트렌드 생성을 트리거하면(또는 예약 스케줄에 의해) 해당 기준일 `TechNews`를 분석해 트렌드 콘텐츠가 생성·저장되어야 한다 | High | Pending |
| FR-02 | 생성된 트렌드는 홈 화면에 "오늘의 개발 트렌드" 카드로 노출되어야 한다 | High | Pending |
| FR-03 | `DailyKnowledge` 생성 시점에 기준일 `DailyTrendInsight`가 **정상 생성되어 있는 경우에 한해** 그 결과가 프롬프트(LLM 호출)에 반영되어야 한다. 트렌드가 없거나 실패 상태이면 FR-04에 따라 트렌드 없이 생성한다 — "가장 최근 트렌드로 대체"하지 않는다(오래된 트렌드가 오늘 지식에 섞이는 것을 방지) | High | Pending |
| FR-04 | 기준일 트렌드가 없거나 트렌드 생성이 실패한 경우에도 `DailyKnowledge` 생성 전체가 실패하지 않아야 한다(가용성 우선, §6 확정) — 이 경우 생성 이력에 "트렌드 미반영" 상태로 기록한다 | High | Pending |
| FR-05 | 기존 `WeeklyAiInsight`, `DailyKnowledge` 단독 조회/노출 기능은 본 기능 추가와 무관하게 회귀 없이 동작해야 한다 | High | Pending |
| FR-06 | 관리자 화면에서 최신 트렌드 생성 결과를 확인할 수 있어야 한다 | Medium | Pending |
| FR-07 | 트렌드 컨텍스트는 프롬프트 템플릿의 `${dailyTrend}` 변수 존재 여부와 무관하게, 서버가 LLM 호출 직전 항상 포함시켜야 한다(예약 생성·수동 생성 두 경로 모두) — §6 확정 | High | Pending |
| FR-08 | 트렌드 재생성 후에도, 이미 생성된 `DailyKnowledge`가 어떤 트렌드를 근거로 만들어졌는지 관리자 화면에서 식별 가능해야 한다(불일치 허용 + 명시, §6 확정) | Medium | Pending |

### 3.2 Non-Functional Requirements

| Category | Criteria |
|----------|----------|
| Traceability | 본 기능은 Plan(본 문서) → Design(`docs/02-design/features/daily-trend-insight.md` 신규 작성) → 코드로 추적 가능해야 함 |
| Backward Compatibility | 트렌드 데이터가 없는 날짜에도 홈 화면·학습 게시물 생성이 오류 없이 동작해야 함 |
| Data Integrity | LLM이 생성한 트렌드 텍스트는 XSS 없이 안전하게 렌더링되어야 함(`th:text` 이스케이프 유지) |
| Sequencing | 스케줄 실행 시 트렌드 생성 단계의 예외는 격리되어 학습 게시물 생성 단계로 전파되지 않아야 함(부분 성공 허용). `GenerationSchedule.markExecuted()`는 기존과 동일하게 `DailyKnowledge` 생성 성공 여부만으로 판단하며, 트렌드 생성 성공/실패는 별도로 이력에만 기록하고 재시도는 관리자 수동 트리거로만 수행한다(자동 재시도 루프 없음) |
| Inherited Risk | 본 기능이 LLM 호출을 1회 더 추가하면서 새로 발생/증폭되는 위험(트랜잭션 내 외부 LLM 호출 구간 확대, 명시적 timeout/retry 부재로 인한 예약 실행 시간 연장, 그로 인한 매분 스케줄 체크와의 중복 실행 가능성, 외부 뉴스 텍스트에 대한 프롬프트 인젝션 미방어)은 Design 문서에서 직접 다룬다. 단, 이 항목은 "본 기능 추가로 새로 생기거나 커지는 위험"에 한정하며, 본 기능과 무관하게 기존에도 있던 날짜 검증 부재·동시 수동/예약 생성 충돌 등은 §4.2 Quality Criteria와 동일하게 범위 밖으로 유지한다(두 절의 경계가 겹쳐 보인다는 Codex 2차 검증 지적을 반영해 문구 명확화) |
| Cost/Input Bound | 트렌드 분석 입력 뉴스 건수·개별 필드 길이에 상한을 둔다(기존 `WeeklyAiInsightService`의 40건/350자 상한과 동등한 수준을 Design에서 확정) |

### 3.3 부분 성공 상태 매트릭스 (Codex 2차 검증 반영)

`DailyKnowledgeGenerationService.executeScheduledGeneration()`은 현재도 "중복이라 스킵"한 경우까지 `success=true`를 반환하고, `ScheduledGenerationExecutor`는 그 `success` 값만으로 `markExecuted()`를 호출한다(기존 동작, 본 기능이 바꾸지 않음). 트렌드 단계가 추가된 뒤의 조합은 다음과 같다.

| 트렌드 결과 | 지식 결과 | `markExecuted()` | 이력 기록 |
|---|---|---|---|
| 성공 | SUCCESS | 호출됨(기존 동작) | 트렌드: 성공 / 지식: 성공+트렌드 반영 |
| 실패/없음 | SUCCESS(폴백) | 호출됨(기존 동작) | 트렌드: 실패 / 지식: 성공+트렌드 미반영 |
| 성공 | SKIPPED(중복) | 호출됨(기존 동작 — `success=true`) | 트렌드: 성공(다음날까지 보존) / 지식: 스킵 |
| 실패/없음 | SKIPPED(중복) | 호출됨(기존 동작) | 트렌드: 실패 / 지식: 스킵 |
| 성공/실패 무관 | FAILED | 호출 안 됨(기존 동작 — `success=false`) | 지식: 실패, 다음 분(minute) 스케줄에서 재시도 대상. 트렌드는 이미 성공했다면 재시도하지 않고 보존된 결과를 재사용 |

트렌드 자체의 자동 재시도 루프는 두지 않는다(§6) — 트렌드가 실패한 날은 관리자 수동 재생성이 유일한 복구 경로다.

## 4. Success Criteria

### 4.1 Definition of Done

- [ ] 관리자가 트렌드를 (재)생성하면 "오늘의 개발 트렌드" 콘텐츠가 저장된다
- [ ] 홈 화면에 최신 공개 트렌드 카드가 노출된다(§6: `WeeklyAiInsight`의 `findLatestVisibleInsight` 패턴과 동일하게 검색 날짜와 무관하게 최신 공개 1건)
- [ ] **[정상 경로]** 기준일 트렌드가 정상 생성된 경우, 같은 날 생성된 `DailyKnowledge`가 해당 트렌드를 반영한 프롬프트로 생성되었음을 확인할 수 있다(프롬프트 스냅샷 또는 생성 결과로 검증)
- [ ] **[폴백 경로]** 뉴스가 없거나 트렌드 생성이 실패한 날에도 `DailyKnowledge` 생성이 정상 완료되고, 이력에 "트렌드 미반영" 상태로 기록된다(FR-04, 이력 기록은 필수 — 저장 위치만 Design에서 확정)
- [ ] 트렌드 재생성 후, 기존 `DailyKnowledge`가 어떤 트렌드를 근거로 생성됐는지 관리자 화면에서 확인 가능하다(FR-08)
- [ ] 활성 프롬프트 템플릿에 `${dailyTrend}` 변수가 없어도 실제 LLM 호출에는 트렌드 컨텍스트가 포함된다(FR-07)
- [ ] 관련 서비스 테스트(신규 트렌드 서비스, `DailyKnowledgeGenerationService` 프롬프트 변경, §6 테스트 매트릭스 항목)가 추가된다

### 4.2 Quality Criteria

- [ ] 레이어드 아키텍처 준수 (Controller → Service → Repository, DTO 분리)
- [ ] 기존 `WeeklyAiInsight`/`DailyKnowledge` 관련 Known Gaps(날짜 검증, race condition 등)는 본 기능 범위가 아니므로 Design 문서에서 구분 기재

## 6. Key Decisions

| 항목 | 결정 | 근거 | 확정 시점 |
|------|------|------|-----------|
| 뉴스 분석 범위 | 기준일 하루치 우선 사용, 뉴스가 3건 미만이면 최근 3일로 확장하는 폴백 적용 | 크롤링 건수가 적은 날에도 최소한의 분석 품질 보장, `WeeklyAiInsightService`의 7일 고정 윈도우와 달리 "일간"이라는 정체성 유지 | 2026-08-13 |
| 트렌드 콘텐츠 형태 | 키워드 3~5개 + 1~2문장 요약(하이브리드) | 스캔 용이성과 `DailyKnowledge` 프롬프트 참조 시 부담 없는 길이를 동시에 확보, `WeeklyAiInsight`(3문단 서술형)와 명확히 차별화 | 2026-08-13 |
| 스케줄 처리 방식 | 별도 cron 신설 없이 `ScheduledGenerationExecutor.executeScheduledGeneration()` 내에서 트렌드 생성(예외 격리) → `DailyKnowledge` 생성 순으로 순차 호출 | 신규 스케줄러 도입에 따른 타이밍 동기화 문제 회피, 기존 실행 흐름에 자연스럽게 편입 | 2026-08-13 |
| 엔티티/테이블명 | `DailyTrendInsight` / `daily_trend_insight` | 기존 `WeeklyAiInsight` 네이밍과 짝을 맞춤 | 2026-08-13 |
| 트렌드 실패 시 우선순위 | **가용성 우선** — 트렌드 없이도 기존 방식으로 `DailyKnowledge` 생성 진행(FR-04) | "매일 게시물이 끊기지 않는 것"이 "트렌드 연결"보다 서비스 안정성에 더 중요하다고 판단. Codex 리뷰에서 FR-03(연결 보장)과 FR-04(가용성)가 모순된다고 지적받아 사용자가 직접 우선순위 결정 | 2026-08-13 (Codex 리뷰 후) |

| 템플릿-트렌드 결합 방식 | **서버가 항상 강제 추가** — 템플릿에 `${dailyTrend}` 변수가 없어도 서버가 LLM 호출 직전 트렌드 컨텍스트를 별도 구역으로 항상 포함(FR-07) | Codex 리뷰: 변수 치환만으로는 기존 활성 템플릿(변수 없음)에서 실제로 반영이 안 될 수 있음을 지적받음. 서버 강제 방식이 "템플릿 관리 실수로 연결이 끊기는" 위험을 원천 차단 | 2026-08-13 (Codex 1차 리뷰 후) |
| 홈 노출 기준 | **최신 공개 트렌드 1건** — 검색 조건(`selectedDate`)과 무관하게 항상 최신 공개된 트렌드만 노출 | `WeeklyAiInsight.findLatestVisibleInsight()`와 동일한 패턴. 신규 날짜 기반 조회 로직 없이 기존 검증된 패턴을 재사용해 구현 리스크를 낮춤. Codex 2차 검증에서 "Design이 아니라 Plan에서 결정할 제품 정책"이라고 지적받아 사용자가 직접 결정 | 2026-08-13 (Codex 2차 리뷰 후) |
| 관리자 화면 배치 | **신규 페이지 없이 `admin/crawling.html`에 탭 추가** — 기존 `[조건 프리셋] [수동 실행] [예약 설정] [주간 AI 인사이트] [크롤링 이력]` 탭 구성에 `[오늘의 개발 트렌드]` 탭을 추가(주간 AI 인사이트 탭과 동일한 UI 패턴: 생성/재생성 트리거, 미리보기 카드, `visible` 토글) | 코드 확인 결과 "크롤링된 뉴스를 분석하는 기능은 크롤링 관리 페이지에 탭으로 묶는다"는 기존 컨벤션이 이미 `weeklyInsight` 탭으로 확립돼 있음 — 같은 성격의 신규 기능이므로 동일 컨벤션을 따름 | 2026-08-13 |

### Codex 교차검증 이력

- **1차 (2026-08-13)**: `codex exec -s read-only`로 최초 Plan을 검증. 판정 Changes Requested, 승인 차단 5건 지적. 이후 문서를 수정해 5건 모두 어떤 형태로든 대응(3건은 사용자 확정 결정, 2건은 best-effort/예외격리 정책으로 Plan 본문에 직접 반영)
- **2차 (2026-08-13)**: 수정된 Plan을 동일 방식으로 재검증. 판정 Changes Requested(유지) — 1차 지적 5건 중 3건은 완전 해소로 재확인, 2건(부분 성공/`markExecuted()` 정책, 재생성 정합성)은 "부분 해소"로 격상. 추가로 8건의 세부 모순(SUCCESS/DoD의 절대적 표현, FR-04와 Open Questions 간 모순, 추출 검증 자기모순, `markExecuted()` 매트릭스 부정확, 수동 미리보기-저장 간 트렌드 정합성, 홈 노출 기준 미정, Known Gap 범위 중복 표현, 문서 내 자기 요약 불일치)을 지적받아 본 버전(0.6)에서 전부 반영

- [ ] 트렌드 분석 입력 뉴스 상한(최대 건수, 정렬 기준, 필드별 길이 제한) — `WeeklyAiInsightService`의 40건/350자 상한을 참고해 구체적 수치 확정
- [ ] "오늘의 개발 트렌드" 카드의 정확한 배치 위치 — 실제 템플릿상 명칭("오늘의 개발 인사이트" 섹션 등)과 매핑해 확정
- [ ] 트렌드 카드 내부 UI 레이아웃 — 키워드 3~5개(배지)와 1~2문장 요약을 카드 안에서 어떻게 배치할지(예: `weekly-ai-insight-card`처럼 레이블 블록 구조를 쓸지, 배지+텍스트를 한 줄로 둘지) 미정
- [ ] 트렌드 단계 성공/실패는 **반드시 기록**(확정, FR-04) — `GenerationHistory`를 확장할지 신규 이력 테이블을 둘지 **저장 위치만** Design에서 확정. 관리자가 "지식은 생성됐지만 트렌드는 실패/미반영"을 구분할 수 있어야 함
- [ ] 테스트 매트릭스: 트렌드/지식 성공·실패 4개 조합, 뉴스 0/1~2/3건 이상 경계, 3일 폴백, 동일 날짜 재생성, 활성 템플릿에 `${dailyTrend}` 없는 경우, 수동 프롬프트 편집 후 동작, 홈 기준일과 트렌드 노출 일치 여부
