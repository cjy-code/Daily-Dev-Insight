## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | `README.md`에 로컬 개발 편의를 위해 관리자 테스트 계정(`admin01`/`1234`)이 그대로 커밋되어 있다. 이 저장소는 공개 GitHub(`cjy-code/Daily-Dev-Insight`)라, 라이브 데모 배포 후에도 그대로 두면 누구나 그 계정으로 관리자 콘솔에 들어가 OpenAI 호출을 반복 트리거할 수 있다 |
| **Solution** | (1) 공개 저장소에 실제 운영 비밀번호가 노출되지 않도록 배포 전 교체(이미 배포 계획 Phase 3에 포함) + (2) **공개 데모용 계정 자체를 "열람 전용"으로 분리**해 생성 권한(POST) 자체를 원천 차단(옵션 C, 1차 방어) + (3) 그래도 뚫릴 경우를 대비한 앱 레벨 일일 상한(옵션 B, 2차 방어) |
| **Function/UX Effect** | 비공개 운영자 계정은 지금처럼 생성 가능, 공개 데모 계정은 결과 열람/확인만 가능하고 생성 버튼 자체가 비활성화되어 보임. 운영자 계정에도 짧은 시간 비정상 반복 호출 시에만 차단 메시지가 뜬다 |
| **Core Value** | 비밀번호 교체 하나에만 의존하지 않는 **다층 방어(defense in depth)** — 공개 계정은 애초에 권한이 없어 비용 발생 자체가 불가능하고, 운영자 계정이 뚫려도 일일 상한과 OpenAI 예산 한도가 손해를 제한한다 |

## 1. 현재 상태 (코드로 확인한 사실)

- 역할은 `USER`/`ADMIN` 단 2단계뿐이다(`users.role`). "제한된 관리자"/"슈퍼 관리자" 같은 세분화된 권한은 없다.
- LLM을 실제로 호출하는 관리자 endpoint는 5개다:

| Endpoint | 트리거 | 호출 대상 |
|---|---|---|
| `POST /admin/generate/preview` | 수동 생성 미리보기 | 텍스트 LLM (+이미지, 설정 시) |
| `POST /admin/generate/preview/image-refresh` | 이미지만 재생성 | 이미지 생성 |
| `POST /admin/generate/save` | 미리보기 저장 | 이미지 생성(설정 시, 저장 시점에 재호출) |
| `POST /admin/weekly-insight/generate` | 주간 인사이트 생성 | 텍스트 LLM |
| `POST /admin/daily-trend/generate` | 일간 트렌드 생성 | 텍스트 LLM |

- **예약 생성(`GenerationSchedule`, 매분 폴링 cron)은 이미 자연적으로 상한이 있다** — 하루 최대 1회(스케줄 조건 충족 시)이므로 별도 제한이 필요 없다. 이번 전략의 대상은 **수동 트리거 5개**뿐이다.
- 현재 이 5개 endpoint 어디에도 횟수 제한/rate limit 로직이 없다 — `ADMIN` role만 통과하면 무제한으로 반복 호출 가능하다.
- Redis가 이미 캐시 용도로 연동되어 있어(`RedisCacheConfig`), 카운터 저장소로 재사용 가능하다(새 인프라 불필요).

## 2. 전략 옵션

### 옵션 A — 비밀번호 교체만 (현재 배포 계획에 이미 포함)
운영 배포 전 `admin01` 비밀번호를 저장소에 없는 값으로 교체.
- 장점: 구현 비용 0
- 단점: **단일 장애점**. 비밀번호가 실수로 다시 커밋되거나, 스크린 공유 중 노출되거나, 데모 시연 중 타이핑을 보이면 그 순간부터 무방비. "혹시 몰라서" 두는 안전장치가 전혀 없음

### 옵션 B — 앱 레벨 일일 사용량 상한 (2차 방어, 옵션 C와 병행)
위 5개 endpoint 진입 시, 오늘 날짜 기준 수동 트리거 횟수를 확인하고 상한 초과 시 차단.
- 카운터 저장 위치 후보:
  - **Redis 카운터** (추천): `INCR llm:manual:count:{yyyy-MM-dd}` + 자정 만료 TTL. 원자적 증가, 구현 간단, 기존 인프라 재사용
  - `GenerationHistory` 테이블 COUNT 쿼리: 별도 인프라 불필요하지만, 매 요청마다 집계 쿼리 필요 + 이력 저장 실패 시 카운트도 같이 틀어질 위험
- 상한 값은 관리자 설정 화면이 아니라 **환경변수**(`LLM_DAILY_MANUAL_LIMIT` 등)로 고정 — 상한 값 자체를 관리자가 UI에서 바꿀 수 있게 하면 그 UI도 같은 공격 표면이 됨
- 초과 시 응답: 기존 `executeAdminAction` 에러 처리 패턴 재사용해 "오늘 수동 생성 가능 횟수를 모두 사용했습니다" 안내

### 옵션 C — 계정 분리 (데모용 열람 계정 vs 실제 운영 계정) — **채택, 1차 방어**
관리자 로그인은 그대로 두되, **공개 데모에 노출하는 계정은 열람 전용(`ADMIN_VIEWER`)으로, 생성 권한이 있는 실제 운영 계정(`ADMIN`)은 비공개로 분리**한다.
- 장점: 근본적으로 공격 표면을 줄임 — 공개 계정이 뚫려도(비밀번호가 새어나가도) 애초에 생성 endpoint 호출 권한이 없어 비용 발생 자체가 불가능
- 최초 검토 시 "`role` 스키마 확장 필요 + 범위가 커서 오늘은 어렵다"고 판단해 out of scope로 미뤘으나, **코덱스 교차검증 결과 이 판단이 틀렸음을 확인**했다:
  - `users.role`은 이미 `VARCHAR2(20)` 단순 문자열(`CustomUserDetailsService`가 그대로 `"ROLE_" + role`로 변환)이라 새 값(`ADMIN_VIEWER`) 저장에 DDL 변경이 불필요하다
  - 생성 endpoint 5개가 `AdminPageController` 한 곳에 모여 있어 권한 분기 추가 범위가 작다
  - 반면 옵션 B(Redis 상한) 단독은 `preview` 1회가 텍스트+이미지 2회 호출로 이어질 수 있고, 공격자가 한도 자체를 소진시켜 정상 데모를 막을 수 있으며, 동시 요청 시 원자적 처리가 필요한 등 생각보다 구현이 복잡함이 드러남
- **주의할 함정 2가지** (코덱스 지적):
  1. 현재 `SecurityConfig`가 `/admin/**` 전체를 `.anyRequest().hasRole("ADMIN")` 단일 매처로 보호하므로, 새 역할을 `SUPER_ADMIN`으로 이름 붙이면 오히려 관리자 화면 접근 자체가 막힌다 → **기존 `ADMIN`을 그대로 "운영자(=사실상 슈퍼 계정)"로 유지**하고, 신규 `ADMIN_VIEWER`(열람 전용)를 추가하는 쪽이 오늘 변경량이 가장 적다
  2. 관리자 로그인 성공 핸들러(`processRoleBoundLoginSuccess`)도 `ROLE_ADMIN`을 정확히 검사하므로, 그대로 두면 `ADMIN_VIEWER` 계정은 로그인 자체가 실패한다 — 함께 조정 필요
- **제한 범위 결정(사용자 확정)**: LLM 생성 5개 endpoint만 좁게 막지 않고, **`ADMIN_VIEWER`는 관리자 콘솔의 POST(변경) 요청 전체를 차단**한다. 이렇게 하면 열람 계정이 회원 권한 변경이나 다른 설정 조작으로 우회하는 것도 함께 막힌다

### 옵션 D — OpenAI 대시보드 자체 지출 한도 (이미 배포 계획 Phase 3에 포함)
프로젝트 전용 키 + 월 예산 상한. 앱이 뚫려도 실제 손해액의 최종 상한선.
- 이번 전략과 별개로 **반드시 병행**해야 하는 항목(이미 계획서에 있음, 여기서는 반복 언급만)

## 3. 추천안

**옵션 A(비밀번호 교체) + 옵션 C(계정 역할 분리, 1차) + 옵션 D(OpenAI 지출 한도)를 데모 필수선으로, 옵션 B(Redis 기반 일일 상한)를 추가 안전장치로 적용**한다.

이유: 네 겹의 방어선(공개 계정은 애초에 생성 권한이 없어 접근 자체가 막힘 → 운영자 계정이 뚫려도 앱이 하루 상한으로 막음 → 그마저 뚫려도 OpenAI가 금액으로 막음 → 비밀번호 교체로 첫 단계 진입 자체를 어렵게 함)이 오늘 안에 구현 가능한 범위에서 가장 효과적이다. (초안 v0.1에서는 B를 주력, C를 후속 과제로 뒀으나 코덱스 교차검증 후 순서를 뒤집었다 — §2 옵션 C 참고)

### 3.1 제안 상한 값 (초안, 확정 필요)

| Endpoint 그룹 | 제안 상한 | 근거 |
|---|---|---|
| 일일 지식 수동 생성(`preview`+`save`+`image-refresh` 합산) | 일 10회 | 정상적인 관리자 사용 패턴(생성→검수→재생성 몇 차례)을 넉넉히 커버 |
| 주간 인사이트 수동 생성 | 일 5회 | 원래도 주 1회 정도만 쓰는 기능 |
| 일간 트렌드 수동 생성 | 일 5회 | 위와 동일 |

이 수치는 근거가 확정된 게 아니라 **초안**이다 — 실제 데모 운영 패턴을 보고 조정 필요.

## 4. Out of Scope (이번 초안에서 다루지 않음)

- `ADMIN`/`ADMIN_VIEWER`를 넘어서는 완전한 RBAC 체계 전면 개편 (지금은 생성 권한 유무 2단계만 다룸)
- IP 기반 차단, WAF 등 네트워크 레벨 방어
- 사용량 초과 시 관리자 알림(이메일/슬랙 등) — 후속 과제로 유효
- 사용자(USER) 계정 관련 제한 — 애초에 USER는 LLM 호출 경로 자체가 없으므로 대상 아님
