## 1. 배포 전 확인된 사실 (오전 세션에서 코드로 검증 완료)

실제 소스 코드를 직접 확인해 아래 2가지를 검증했다 — 공개 배포 시 가장 걱정되는 지점인데 이미 안전하다.

- **공개 회원가입 기능 자체가 없다.** `signup`/`register` 관련 컨트롤러가 존재하지 않음(테스트 계정만 시드로 존재: `user01`/`admin01`). 무단 가입 스팸 위험 없음.
- **LLM(OpenAI) 호출은 전부 관리자 전용 경로에서만 발생한다.** `controller/` 하위 공개 컨트롤러(`InsightPageController`, `DailyInsightRestController` 등) 어디에도 `generateKnowledge`/`generateAndStoreImage`/`generateWeeklyInsight`/`generateDailyTrend` 호출이 없음. 즉 사이트를 공개해도 방문자가 트래픽만으로 OpenAI 비용을 발생시킬 수 없다 — 비용은 관리자가 실제로 트리거한 만큼만 나간다.

→ 이 2가지 덕분에 "배포 전에 반드시 코드를 더 고쳐야 하는" 보안 블로커는 없다. 아래 계획은 전부 **인프라/설정** 작업이다.

## 2. 현재 로컬 상태 (오전 세션 종료 시점)

- 앱은 로컬에서 `./gradlew bootRun`으로 정상 기동, `docker-compose.yml`의 Oracle XE + Redis 컨테이너와 연동 확인됨
- `OPENAI_API_KEY`는 로컬 세션에 **환경변수로만** 설정해둔 상태 — 터미널/프로세스가 꺼지면 사라짐. 저장소 어디에도 커밋되어 있지 않음(의도적). 집에서 재개 시 실제 배포 서버에 새로 설정해야 함.
- 오늘 오전 실제 OpenAI 호출로 생성 품질 검증 완료: 마크다운 렌더링, 이미지-본문 연관성(제목/요약 변수 반영) 모두 정상 확인됨
- 오늘 만든 데모용 콘텐츠: id=23(2026-08-14), id=24(2026-08-15 테스트), id=25(2026-08-16 테스트) — 25번은 이미지-본문 매칭 검증용으로 만든 것이라 실제 배포 전 날짜/품질 재검토 필요

## 3. 실행 체크리스트 (Phase 순서대로)

### Phase 0 — 호스팅 계정 준비 (사용자 직접, Claude 대행 불가)
- [ ] Oracle Cloud 계정 신규 생성 (Always Free 티어) — 본인인증/카드 등록 필요할 수 있음, 시간 여유 두고 진행
- [ ] Always Free VM 인스턴스 1개 생성 (Ampere A1 또는 AMD 상시 무료 shape)

### Phase 1 — 서버 준비
- [ ] VM에 SSH 접속 확인
- [ ] Docker + Docker Compose 설치
- [ ] 저장소 clone (또는 필요한 파일만 전송)
- [ ] 방화벽: 80/443만 외부 오픈, 1521(Oracle)/6379(Redis)는 컨테이너 내부 통신만 허용하고 외부 차단

### Phase 2 — 애플리케이션 배포 설정
- [ ] 서버에 `.env` 또는 systemd/docker 환경변수로 `OPENAI_API_KEY`, `DB_PASSWORD` 등 설정 (저장소에 커밋하지 않음)
- [ ] 기존 `docker-compose.yml`로 Oracle+Redis 기동, `docs/sql/` 마이그레이션 순서대로 적용 (README §9.2 순서 그대로)
- [ ] Nginx 또는 Caddy 리버스 프록시 설정 (9090 → 80/443)
- [ ] Let's Encrypt로 HTTPS 인증서 발급 (도메인은 클라우드 기본 주소/무료 서브도메인 사용하기로 결정됨 — §5 참고)
- [ ] `CRAWLER_THUMBNAIL_UPLOAD_DIR`(`./uploads`)를 Docker volume으로 마운트 — 컨테이너 재시작 시 업로드 이미지 유실 방지

### Phase 3 — 안전장치
- [ ] OpenAI 대시보드에서 이 프로젝트 전용 프로젝트 키로 재발급 + **월 지출 한도(budget limit)** 설정 (예약 생성이 매일 자동 실행되므로 반드시 필요)
- [ ] `admin01` 비밀번호를 로컬 테스트용(`1234`)에서 실제 운영 비밀번호로 교체
- [ ] Oracle DB 볼륨 백업(스냅샷) 최소 1회 설정

### Phase 4 — 콘텐츠 준비
- [ ] §2에 기록된 테스트용 게시물(id=24, 25) 정리 — 데모에 안 어울리면 삭제하거나 재생성

## 4. 왜 이 방식인가 (대안을 채택하지 않은 이유)

- **관리형 DB(Oracle Autonomous 등)로 전환하지 않는 이유**: 지갑(wallet) 기반 TLS 연결 방식이라 지금의 단순 JDBC thin URL 연결 코드와 `docs/sql/`의 PL/SQL 마이그레이션 10개, `OracleSchemaMigrationRunner`를 다시 손봐야 함. 지금 단계에서는 비용 대비 이득이 적음.
- **PostgreSQL 등으로 마이그레이션하지 않는 이유**: 이미 Oracle 전용 문법으로 짜인 마이그레이션 스크립트 자산이 있어 재작성 리스크가 큼.
- **클라이언트 JS 기반 배포(정적 호스팅)를 쓰지 않는 이유**: 이 프로젝트는 Thymeleaf 서버사이드 렌더링 + Spring Security 세션 기반이라 정적 호스팅 자체가 불가능. 반드시 서버(VM 또는 컨테이너 플랫폼)가 필요.

## 5. 이미 결정된 사항

| 항목 | 결정 | 비고 |
|---|---|---|
| 도메인 | 무료/클라우드 기본 주소로 우선 공개 | 나중에 정식 도메인으로 교체 가능 |
| 클라우드 계정 | Oracle Cloud 신규 가입 필요 | Phase 0에서 사용자가 직접 진행 |
| DB/인프라 방식 | 기존 docker-compose 스택을 VM에 그대로 이전 | 코드 변경 최소화 |

## 6. 남은 리스크 (README §14 Known Issues 중 배포와 관련 있는 것만)

- 부하 테스트 미실시 — 데모 트래픽(소수 방문자) 수준에서는 문제 없을 것으로 예상되나 확언은 불가
- LLM 호출 타임아웃/재시도 미구현 — 예약 생성이 실패해도 다음 분(minute) 스케줄에서 재시도되는 기존 로직으로 커버되긴 함
- SSRF 방어 후에도 DNS 리바인딩 잔여 위험 존재 — 크롤링 대상 URL은 관리자가 직접 설정하므로 공개 배포 자체의 긴급 블로커는 아님
